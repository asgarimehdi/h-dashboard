# Persian Search & Normalization

| Canonical repo: https://github.com/asgarimehdi/h-dashboard (base branch `beta`).
| Every clone of it is a fork — never hardcode a fork URL or branch, read
| `git remote -v` / `git branch --show-current` first.
| Split out of `AGENTS.md` on 2026-10-16; that file keeps the one-line rules and
| the map of where each topic lives.

Everything the search stack needs. `normalizeForSearch()` / `escapeLikeWildcards()` /
`foldSeparatorsSql()` / `foldedTerm()` live in `app/Traits/PersianNormalizer.php`; the models
normalize on save carry the PersianNormalizer trait.

| Gotcha | Details |
|---|---|
| Search | Multi-word queries split and matched independently via `scopeFilterSearch` |
| `normalizeForQuery` | Use `PersianNormalizer::normalizeForQuery()` for user-supplied LIKE queries ONLY on columns the model normalizes on save (`Person` fields, `Hardware` fields like `pc_name`/`type`/`os`/`comments`) — combines Persian normalization + wildcard escaping. Do NOT inline `str_replace(['%', '_'], ...)`. Lookup-table columns (`units.name`, `semats.name`) have no save hook: query their **stored** folded column (`units.name_folded`, `semats.name_folded`) and the term with `foldedTerm($input)` (#815, #1482) — see the "fold the COLUMN" row below. `persons` has the same stored columns (`f_name_folded`, `l_name_folded`, `full_name_folded`, `full_name_rev_folded`): it covers hook-written rows *and* rows that bypassed it — `PersonsTableSeeder` inserts through `DB::table('persons')->insert(...)`, so a seeded name keeps its raw code points, and a `saving` hook is not an invariant (#940). `radifs.name`, `tahsils.name`, `estekhdams.name` have no folded column (and no folded search site today) |
| `PersianNormalizer` trait | Located at `app/Traits/PersianNormalizer.php`. Methods: `normalizeForSearch()` (Arabic→Persian + Unicode), `escapeLikeWildcards()`, `normalizeForQuery()` (normalize + escape combined) |
| Persian search folds the COLUMN — at write time, in a stored generated column | `normalizeForQuery()` rewrites the search term (ZWNJ U+200C → space; آ/أ/إ U+0622/0623/0625 → ا) but the stored text keeps the original code points, so `LIKE` stops matching — a unit named "حرفه" + ZWNJ + "ای" or "آموزش" becomes invisible to its own filter. Postgres `LIKE` has only `%`/`_` and **no character-class syntax**, so `[ … ]` is literal and "either spelling" is unexpressible. `PersianNormalizer::foldSeparatorsSql()` (nested `regexp_replace` applying the same `charMap()` as `normalize()`, plus one `translate()` applying `digitMap()` so Persian/Arabic-Indic digits fold to Latin exactly as `normalizeForSearch()` does) is still the definition, but since #1482 it runs **once per row at write time**: migration `2026_11_14_000001_add_folded_columns_for_persian_search.php` adds `GENERATED ALWAYS AS (foldSeparatorsSql(...)) STORED` columns on `persons`/`units`/`semats` plus plain `gin_trgm_ops` indexes on them. Query the stored column against `foldedTerm($input)` — a generated column is maintained by PostgreSQL on every write path, including raw `DB::table()->insert()`. `FoldedColumnsTest` compares the live catalog back against the trait, so changing `charMap()`/`digitMap()` without rebuilding the columns fails loudly instead of silently serving stale rows. Replace ZWNJ with a SPACE, never `''` — deleting it makes the regex eat the next letter ("حرفه" + ZWNJ + "ای" → "حرفهای") |
| `LIKE '%term%'` is index-seekable only on a **stored** folded column | A bare `LIKE '%…%'` on an unfolded column is a Seq Scan (or, with a trigram index, a Bitmap Index Scan — trigram indexes do serve infix `LIKE`). Wrapping the column in `foldSeparatorsSql()` at query time is **never** index-seekable, not even by a trigram index on the expression, and its lossy recheck would re-run the eight fold calls per candidate row — so never fold at query time on `persons`/`units`/`semats`; use the stored column. `units` (834 rows) and `semats` (56 rows) are small enough that the planner legitimately picks a Seq Scan: only parity matters there, not the plan shape |
| Build the search term list ONCE, from `normalizeForSearch()` — never index a second list by its positions | `normalizeForSearch()` maps ZWNJ/ZWJ **and** any `\s+` run to a SPACE, so a Persian compound like «خانه بهداشت» or «حرفه ای» yields **more** terms than the raw string has words. Building `$rawTerms`/`$foldedTerms` from the raw string and reading `$foldedTerms[$i]` at `$terms`' positions walks off the end: `ErrorException: Undefined array key` → 500 on `GET /kargozini/persons/export` for anyone typing a ZWNJ compound and clicking «خروجی اکسل» (regression from #815, fixed by #940). Split `normalizeForSearch($search)` once and call `foldedTerm($term)` **inside** the loop, exactly like `resources/views/livewire/kargozini/person.blade.php`. Do **not** derive the list from `normalizeForQuery()` and fold again — that output is already escaped, so the second `escapeLikeWildcards()` double-escapes `%`/`_` into `\%\%` and the search silently stops matching |
